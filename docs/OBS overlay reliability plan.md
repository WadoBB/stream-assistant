# Automate the Refresh OBS Already Needs

**Bottom line:** the overlays go stale because of a maintainer-confirmed, still-open bug in the Chromium 127 build (CEF 6533) that OBS 31.0 through 32.2.x bundle, and nothing StreamElements, Streamlabs or Streamer.bot do in their pages escapes it. OBS maintainers reproduced the freeze on Windows 11 / OBS 32.0.2 using StreamElements widget URLs, and reduced it to a trivial page with looping muted video; they attribute it to Chromium/CEF and say the fix is the CEF update that ships in OBS 33.0 ([obs-studio #12796](https://github.com/obsproject/obs-studio/issues/12796), [comments](https://api.github.com/repos/obsproject/obs-studio/issues/12796/comments)). The commercial overlays' transports are not stronger than ours: StreamElements and Streamlabs use Socket.IO v2 over WebSocket with a 25-second library heartbeat, and Streamer.bot's official client has no heartbeat at all ([SE Websockets.md](https://github.com/StreamElements/api-docs/blob/main/docs/Websockets.md), [Streamlabs Socket API](https://dev.streamlabs.com/docs/socket-api), [StreamerbotClient.ts](https://raw.githubusercontent.com/Streamerbot/client/main/packages/client/src/ws/StreamerbotClient.ts)); our 1-second named ping plus 8-second watchdog is stricter than any of them. The decisive clue is in our own incident log: a manual Browser Source refresh fixed the stale Car Card every single time. That manual action is `refreshnocache`, which obs-websocket v5 can press remotely with `PressInputPropertiesButton` ([obs-websocket protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md), [obs-browser-plugin.cpp](https://github.com/obsproject/obs-browser/blob/master/obs-browser-plugin.cpp)). The plan that follows is therefore ranked around one idea: first add a tiny render-acknowledgement diagnostic so we can finally tell whether the page stopped *receiving* or stopped *painting*, then have `controller.py` press the refresh button on the Gaming PC's OBS whenever an event is written and the page has not acknowledged it within ~1.5 seconds. That turns the proven human fix into an automatic one, keeps SSE as the fast path, costs roughly 60 lines of Python plus an OBS checkbox, and is verifiable on the next stream from the existing `/logs` endpoint. The largest honest caveat is that the perceived "StreamElements is reliable in the same OBS" comparison is unverifiable and probably a sample-size effect: the Car Card fires dozens of times a night, a follow alert a handful, and the only public reproduction of this freeze on our exact OBS version used StreamElements pages.

## Three different stalls hide behind one symptom

"The browser source stopped updating" is not one bug. The research separates three mechanisms, and only one of them is what our pages can observe from JavaScript. The first is JavaScript timer throttling: obs-browser simulates the Page Visibility API and tells a page it is hidden whenever the source is not showing anywhere, and Chromium then clamps `setTimeout`/`setInterval` to once per second, dropping to once per minute after five minutes for self-rescheduling chains, while `requestAnimationFrame` stops entirely ([obs-browser PR #168](https://github.com/obsproject/obs-browser/pull/168), [obs-browser #307](https://github.com/obsproject/obs-browser/issues/307), [Chrome 88 timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/)). obs-browser does not pass `--disable-background-timer-throttling` to CEF, and the OBS launch flag that once worked around it has been reported dead since OBS 23.1 ([browser-app.cpp](https://raw.githubusercontent.com/obsproject/obs-browser/master/browser-app.cpp), [OBS forum 85359](https://obsproject.com/forum/threads/browser-source-background-tabs-and-javascript-timing.85359/)). **This mechanism cannot explain our failure**, because both overlays sit in the live Program scene the whole session; a source visible on Program is not hidden in CEF's eyes, and the throttling policies explicitly do not touch sockets, only timers ([blink-dev intensive throttling](https://groups.google.com/a/chromium.org/g/blink-dev/c/8En_5DqV_fU/m/I8e9vaecAgAJ)).

The second mechanism is deterministic page teardown. "Shutdown source when not visible" calls `DestroyBrowser()` the moment a source stops showing, which kills the SSE connection and all page state; "Refresh browser when scene becomes active" reloads the page on a scene switch; and the Refresh button or hotkey calls `ReloadIgnoreCache()` ([obs-browser-source.cpp](https://raw.githubusercontent.com/obsproject/obs-browser/master/obs-browser-source.cpp), [OBS KB: Browser Source](https://obsproject.com/kb/browser-source)). These are visibility-driven, never time-driven, so they also cannot make a source that stays visible go quiet, but they matter enormously for the plan: a remote `refreshnocache` is a silent no-op on a source with no live browser, because `ExecuteOnBrowser` guards on `if (!!cefBrowser)` and obs-websocket still reports success ([obs-browser-source.cpp](https://github.com/obsproject/obs-browser/blob/master/obs-browser-source.cpp)).

The third mechanism is the real one: a compositor or render stall where JavaScript runs, the socket is up, DOM updates happen, and the frame OBS receives is never repainted again. In hardware-accelerated mode OBS receives frames only through the shared-texture `OnAcceleratedPaint` path and `OnPaint` returns early, so a stall in that path is invisible to the page and leaves nothing in any log, which matches every report's "no errors" ([browser-client.cpp](https://raw.githubusercontent.com/obsproject/obs-browser/master/browser-client.cpp)). Maintainer PatTheMav reduced it to a page of looping muted `.webm` files and called it a Chromium/CEF problem; another reporter reproduced it in stock Chromium with two tabs, not Firefox ([#12796 comments](https://api.github.com/repos/obsproject/obs-studio/issues/12796/comments)). This is also where the project's own CLAUDE.md needs a correction: the issue closed "not planned" was #11327, a Streamlabs-URL report the maintainers declined to troubleshoot ([obs-studio #11327](https://github.com/obsproject/obs-studio/issues/11327)); the tracked issue, #12796, is **open, labelled confirmed, and reproduced by maintainers on our exact OBS version and OS**. No 32.x release fixes it; 32.0.1 only repaired a scene-switch regression that 32.0.0 introduced ([OBS 32.0.1 release](https://github.com/obsproject/obs-studio/releases/tag/32.0.1)). The 2026-09-18 observation that the identical page ran flawlessly all night in Brave but needed refreshes in OBS fits mechanism three exactly: a foreground Brave tab never enters the offscreen-rendering compositing path at all.

A fourth contributor is specific to our hardware. On Windows 11, OBS 32.0.2/32.0.4 users found that Windows drops the `obs-browser-page.exe` child processes into Efficiency Mode when OBS loses focus, cutting their performance by roughly 80 percent; maintainer WizardCM is planning a PR to disable renderer backgrounding, and the interim fix is to set those processes to High priority and untick Efficiency Mode in Task Manager ([obs-studio #12982](https://github.com/obsproject/obs-studio/issues/12982)). During a race the game window has focus and OBS does not, so this applies to us by default. The reports describe stutter rather than hard freezes, so it is a plausible aggravator, not a proven cause.

## The commercial overlays have no secret, and they freeze too

Every public fact about how StreamElements, Streamlabs and Streamer.bot keep their overlays alive points to ordinary library defaults, not engineering around OBS. StreamElements' documented realtime layer is Socket.IO v2 forced onto the `websocket` transport against `realtime.streamelements.com`, authenticated with the overlay token, with the hosted page re-dispatching socket events to widgets as DOM `CustomEvent`s; its `disconnect` handler in the official example is a comment saying "Reconnect" ([SE Websockets.md](https://github.com/StreamElements/api-docs/blob/main/docs/Websockets.md), [c4ldas SE socket docs](https://c4ldas.github.io/streamelements-api/socket.html)). Whatever it inherits is Socket.IO's default: reconnect from 1 s backing off to 5 s with jitter, infinite attempts, and a heartbeat of 25 s ping interval with a 5 s (v2) or 20 s (v4) timeout ([socket.io v2 client](https://socket.io/docs/v2/client-api/), [socket.io v4 server options](https://socket.io/docs/v4/server-options/)). Streamlabs pins Socket.IO 2.0.3 in its docs and offers no heartbeat guidance at all; its official troubleshooting for alerts that stop appearing is to remove and re-add the browser source, toggle Browser Source Hardware Acceleration, and clear the obs-browser cache, which is the clearest possible admission that they rely on OBS behaving rather than on anything page-side ([Streamlabs Socket API](https://dev.streamlabs.com/docs/socket-api), [Streamlabs Alerts troubleshooting](https://streamlabs.com/content-hub/post/alertswidget-troubleshooting)). Streamer.bot's `@streamerbot/client` is a raw WebSocket with `autoReconnect: true`, infinite retries, a linear `setTimeout(min(30000, n × 1000))` backoff, and, confirmed in source, no ping, no visibility handling and no Web Worker ([StreamerbotClient.ts](https://raw.githubusercontent.com/Streamerbot/client/main/packages/client/src/ws/StreamerbotClient.ts), [Streamer.bot client config](https://streamerbot.github.io/client/api/config)).

| Vendor | Transport | Liveness check | Reconnect | Worker / visibility / rAF tricks |
|---|---|---|---|---|
| StreamElements | Socket.IO v2 WSS | library ping ~25 s | 1→5 s jittered, infinite | none documented |
| Streamlabs | Socket.IO v2 WSS | library ping ~25 s | library default | none; official fix is re-add source |
| Streamer.bot | raw `ws://127.0.0.1:8080` | **none** | 1 s × attempt, cap 30 s | none (confirmed in source) |
| Ours | SSE, `/overlay/stream` | named `ping` every ~1 s, 8 s client deadline | EventSource native + watchdog | 10-minute self-reload |

Set against that table, our pages are the strictest of the four. None of the vendors' public code or docs use Web Worker timers, `window.obsstudio` events or AudioContext tricks, and the minified first-party overlay bundles are token-gated and were not inspected, so any claim that they do something cleverer internally is unverifiable in both directions; what is verifiable is that their documentation treats OBS stalls as the user's problem. More damning for the "SE is reliable" premise, the maintainers' reproduction of the freeze on Windows 11 / OBS 32.0.2 used StreamElements widget URLs, the 2024 forum thread that first popularised the symptom was about Streamlabs chat and Twitch alert sources, and a commenter on #12796 reports it with "5+ SSE sources" ([#12796 comments](https://api.github.com/repos/obsproject/obs-studio/issues/12796/comments), [OBS forum 180554](https://obsproject.com/forum/threads/browser-source-stops-updating-after-a-while.180554/)). The honest reading is that StreamElements alerts on the Gaming PC are not immune; they are observed far less often. The Car Card fires on every garage browse and was therefore the first page to reveal a per-source, random-onset freeze, while a follow or sub alert on a small stream fires a few times a night and a missed one is easy to attribute to no one having followed.

Switching our transport would buy nothing. EventSource and WebSocket share every half-open failure mode: the browser cannot send protocol pings on either, `readyState` stays OPEN on a dead path for both, and both need exactly the application-level heartbeat plus client deadline we already have, while EventSource gives automatic reconnection free and WebSocket does not ([WHATWG SSE spec](https://html.spec.whatwg.org/multipage/server-sent-events.html), [websocket.org heartbeat guide](https://websocket.org/guides/heartbeat/)). The one place SSE is genuinely weaker, Chromium's six-connections-per-host cap on HTTP/1.1, is not in play at two streams in OBS and two in Brave, and the 2026-09-18 seven-reload test already showed no queuing ([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), [Chromium socket pool](https://chromium.googlesource.com/chromium/src/net/+/master/socket/client_socket_pool_manager.cc)). Werkzeug's threaded dev server is unsupported for production but has no documented failure at this scale; the one real trap is that a dead client is only noticed when a write fails, which our 1-second ping guarantees ([Werkzeug serving docs](https://werkzeug.palletsprojects.com/en/stable/serving/), [werkzeug #2397](https://github.com/pallets/werkzeug/issues/2397)). Swapping to waitress without raising its default four-thread pool would actually break us, since four long-lived streams would exhaust it.

## What OBS settings actually do, and the one lever we have not pulled

Only three per-source controls cause deterministic page teardown: the two visibility checkboxes and the Refresh button. Everything else changes the rendering path or rate. With "Use custom frame rate" off, obs-browser pins the page's windowless frame rate to the canvas FPS every tick; "Control audio via OBS" reroutes audio through the mixer and mutes the CEF host ([obs-browser-source.cpp](https://raw.githubusercontent.com/obsproject/obs-browser/master/obs-browser-source.cpp)). The global "Enable Browser Source Hardware Acceleration" switch selects between the shared-texture frame path and the software `OnPaint` path, which is why toggling it is the forum's universal first suggestion and why reports go both ways: it swaps one Chromium code path for another rather than fixing either ([obs-browser-plugin.cpp](https://github.com/obsproject/obs-browser/blob/master/obs-browser-plugin.cpp), [OBS forum 125860](https://obsproject.com/forum/threads/browser-source-freeze.125860/)). Multi-GPU Windows machines additionally need `obs-browser-page.exe` on the same GPU as OBS or sources go black ([OBS wiki: Laptop Troubleshooting](https://github.com/obsproject/obs-studio/wiki/Laptop-Troubleshooting-New)). For an always-visible overlay the evidence-backed configuration is therefore: Shutdown-when-not-visible **off** (so a remote refresh always has a browser to act on), Refresh-when-scene-active **on** (free recovery on every scene switch, which is precisely the moment #12796 correlates with freezes, and no cost while the scene stays live), custom FPS off, and HW acceleration flipped only as a controlled experiment after the bigger changes land.

The lever we have not pulled is external control. The user's log says it plainly: a manual Browser Source refresh "always then showed the correct car." That button is registered in obs-browser as the `refreshnocache` property whose callback is `BrowserSource::Refresh()`, a `ReloadIgnoreCache()` on the existing CEF browser, and obs-websocket v5 exposes it through `PressInputPropertiesButton` with `inputName` and `propertyName: "refreshnocache"` ([obs-browser-plugin.cpp](https://github.com/obsproject/obs-browser/blob/master/obs-browser-plugin.cpp), [obs-websocket protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)). The dedicated 4.x refresh request was dropped in 5.x and the feature request closed "not planned," but the button press is the canonical replacement and is what the community tooling uses: the xObsBrowserAutoRefresh filter (builds for OBS 32+) and the `refresh-browser-sources.lua` script both find and click that same button ([obs-websocket #1171](https://github.com/obsproject/obs-websocket/issues/1171), [xObsBrowserAutoRefresh](https://github.com/YorVeX/xObsBrowserAutoRefresh), [refresh-browser-sources.lua](https://github.com/rse/obs-scripts/blob/master/refresh-browser-sources.lua)). This matters because a warm reload inside the existing browser is the lightest possible recovery, and because a reload is the only remedy any source reports working against the compositor stall; a page cannot observe its own frozen frame from JavaScript, so the in-page 10-minute `location.reload()` is a blind timer that also runs on the very main-thread scheduler the bug lives in.

Two stronger OBS-side pushes exist and are worth knowing even though the plan does not lead with them. `SetInputSettings` with a changed `url` string (a query-string difference counts, same string is a no-op) makes obs-browser destroy and recreate the whole CEF browser, a cold start that also lets the URL carry the alert payload so the page needs no server connection at all; `SetSceneItemEnabled` off-then-on does the same when Shutdown-when-not-visible is on ([obs-browser-source.cpp](https://github.com/obsproject/obs-browser/blob/master/obs-browser-source.cpp), [protocol.md](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)). Streamer.bot wraps both as the "Set Browser Source Url" and "Set Source Visibility State" sub-actions, can send anything else via "OBS Raw," and accepts an external `POST /DoAction` on its HTTP server at `127.0.0.1:7474` with no documented authentication ([Set Browser Source Url](https://docs.streamer.bot/api/sub-actions/obs-studio/sources/set-browser-source-url), [OBS Raw](https://docs.streamer.bot/api/sub-actions/obs-studio/raw), [DoAction](https://docs.streamer.bot/api/http/requests/do-action)). The cold-start path is held in reserve because no source publishes reload timings, the recreate is plausibly 0.5–2 s versus low hundreds of milliseconds for a warm reload, rapid repeated refreshes are themselves a known way to kill rendering on both 27.x and the 33.0 betas, and the Car Card's garage-browsing burst of car changes would turn every change into a blank-then-animate cold start ([obs-browser #356](https://github.com/obsproject/obs-browser/issues/356), [obs-studio #13982](https://github.com/obsproject/obs-studio/issues/13982)).

For the Python side, obsws-python 1.8.0 (July 2025, sync `ReqClient`, request names snake_cased) is the maintained choice; simpleobsws 1.4.3 by obs-websocket's own maintainer is the async alternative, and the old obs-websocket-py targets the 4.x protocol and must not be used ([obsws-python](https://pypi.org/project/obsws-python), [simpleobsws](https://pypi.org/project/simpleobsws/)). The server is enabled under Tools → WebSocket Server Settings, port 4455, authentication on by default; the AI PC must be able to reach the Gaming PC on that port, which means a Windows Firewall rule and, per several guides, possibly a bind-address change, neither of which could be verified against the OBS 32 dialog from primary sources ([obs-websocket protocol auth](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md), [videosdk obs-websocket guide](https://www.videosdk.live/developer-hub/websocket/obs-websocket)). Because `_sse_stream()` already forced `threaded=True`, a blocking client call from `write_race()`'s thread or a request handler is safe.

## OBS 33 is the real fix, and it is not ready yet

OBS 33.0 jumps CEF from 127/6533 to 150/7871 with the Chrome Runtime, merged 2026-09-18 after what the project describes as more than a year of work, and the maintainers explicitly framed a CEF update as the precondition for addressing the freeze ([obs-studio PR #13900](https://github.com/obsproject/obs-studio/pull/13900), [obs-browser PR #523](https://github.com/obsproject/obs-browser/pull/523), [linuxiac on OBS 33](https://linuxiac.com/obs-studio-33-nears-release-heres-what-to-expect/)). Beta 6 was out on 2 October 2026, and the betas have already introduced a new browser-source regression where two quick refreshes turn the source black, which does not occur on 32.2.2 ([obs-studio releases](https://github.com/obsproject/obs-studio/releases), [obs-studio #13982](https://github.com/obsproject/obs-studio/issues/13982)). The right stance is to treat 33.0 as the most likely eventual cure, upgrade once it is stable and that regression is closed, and keep every mitigation below in place through the transition, because none of the 33 beta notes claim the intermittent freeze is fixed and a refresh-based plan would be exactly what that regression punishes if hammered.

## Conclusion

The question "why does StreamElements work when we don't" turns out to be the wrong question: on this OBS build the honest answer is that it probably doesn't, and we only notice ours because the Car Card gives us thirty chances a night to see the freeze instead of three. What that reframing changes is the engineering target. We stop trying to make the page itself unstallable, which no transport, heartbeat or timer trick can achieve against a compositor that silently keeps the last texture, and instead treat OBS as a device we drive: the page stays the fast path, and the server, which can see when a page failed to acknowledge an event, presses the same Refresh button the streamer has been pressing by hand. That also finally gives the project a measurement it has never had. Every entry in the incident log since September 12 ends in some version of "not yet confirmed against a real OBS session"; a two-line render acknowledgement closes that loop and tells us, per missed event, which of the three mechanisms we are actually fighting, which is the one fact that decides whether a transport change, a settings change or an OBS upgrade would have mattered.
